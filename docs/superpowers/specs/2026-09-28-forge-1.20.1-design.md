# Diamond Vending on Forge 1.20.1 — Design Spec

- **Date:** 2026-09-28
- **Status:** Design approved 2026-09-28 · written spec awaiting review
- **Extends:** [`2026-09-23-diamond-vending-design.md`](2026-09-23-diamond-vending-design.md) (the main spec). Everything
  there holds on 1.20.1 unless this document says otherwise.
- **Issue:** [#2 Forge 1.20.1 support](https://github.com/benethcopilot/diamondvending/issues/2)

## 1. Goal

The same mod, with every v1.0 feature, as a fifth jar for **Minecraft 1.20.1 on Forge**, so it drops into the 1.20.1
Forge modpacks we play (Better MC BMC4 and others; the owner's six 1.20.1 Forge packs run Forge 47.2.17–47.4.22).

### Success criteria

1. Five jars build from one codebase: the four from the main spec plus **1.20.1 Forge**.
2. The Forge jar needs nothing but Forge **47.2.0 or newer** on Minecraft 1.20.1, and works on dedicated servers.
3. Every feature in the main spec works on 1.20.1: placing, protecting, dyeing and breaking; buying, credit, coin return
   and the tray; the display, drop animation and hover tooltip; the setup screen; catalogs; currency; setup kept on the
   item; the manual.
4. All unit tests and every shared GameTest pass on all five targets.
5. v1.1.0 is released with the five jars.

### Decisions

| Topic | Decision |
|---|---|
| Structure | A fifth Stonecutter node, **`1.20.1-forge`**, in the same source tree — not a branch |
| Loader | **Forge** only. Fabric 1.20.1 and the NeoForge 1.20.1 fork are out of scope |
| Build plugin | NeoForge **ModDevGradle, Legacy Forge plugin** (`net.neoforged.moddev.legacyforge`), same version as the NeoForge nodes |
| Loader floor | **Forge 47.2.0**, and the node compiles against exactly that version, so no newer API can slip in |
| Java | 1.20.1 runs on **Java 17**: every source file shared with that node is Java 17 |
| Item data | 1.20.1 has no item components: the same data lives in item **NBT** (§5) |
| Features | Full parity with v1.0; no 1.20.1-only features |
| Version | **1.1.0** for all five jars |

## 2. Build

- `settings.gradle.kts`: `match("1.20.1", "forge")` adds node `1.20.1-forge`, built by a new
  **`build.forge.gradle.kts`**. Its shape follows `build.neoforge.gradle.kts`: main and gametest source sets, the
  `client`, `server` and `gameTestServer` runs with the same run folders, `generateArt` is not registered (art is
  generated from `26.1-neoforge`), the same test system properties, `buildAndCollect`, and `publishMods`.
- `stonecutter.gradle.kts`: the loader constant list becomes `fabric`, `neoforge`, `forge`, so code can say
  `//? if forge`. Version checks for 1.20.1 are written `//? if <1.20.5` / `>=1.20.5` (1.20.5 is where item
  components, registry-aware saving and the newer block methods arrived), so a later Fabric 1.20.1 node reuses them.
- `stonecutter.properties.toml`: a `["1.20.1"]` table (`mod.mc_releases = ["1.20.1"]`) and a `[forge."1.20.1"]` table
  with `mod.mc_compat = "[1.20.1,1.20.2)"`, `deps.forge_loader = "47.2.0"` and `deps.forge_loader_min = "47.2.0"`.
- Java 17 toolchain for the node; Gradle's toolchain resolver downloads it (as it does Java 21 today).
- The jar players get is the **reobfuscated** one that runs in a real Forge install; that is the jar CI uploads and
  the release publishes.
- **Metadata:** Forge reads `META-INF/mods.toml` (not `neoforge.mods.toml`): `loaderVersion = "[47,)"`, dependencies
  on `forge` (`mandatory = true`, `versionRange = "[${forge},)"`) and `minecraft` (`[1.20.1,1.20.2)`), filled in by
  `processResources` like the NeoForge file. A `pack.mcmeta` (pack format 15) ships in the 1.20.1 resources.
- **Resources:** JSON whose format differs on 1.20.1 lives in **`src/main/resources-1.20.1/`**, alongside the existing
  `resources-1.21.1/` and `resources-26.1/`: both recipes, both recipe advancements, the item model and the example
  catalog. Shared data files keep one copy: when building the Forge jar, `processResources` moves them to 1.20.1's
  folder names — `tags/item` → `tags/items`, `tags/block` → `tags/blocks`, `recipe` → `recipes`, `advancement` →
  `advancements` and (for the game tests) `structure` → `structures`. A file whose folder has no 1.20.1 name fails
  the build instead of being shipped where 1.20.1 won't find it.
- `neoforge-mutex` (one Minecraft-artifact job at a time) also covers the Forge node's equivalent task.

## 3. Java 17

- 1.20.1 packs run Java 17, so the node compiles with `--release 17`, and every file it compiles — main, gametest and
  test sources — must be Java 17. Today that means rewriting the pattern-matching `switch` statements
  (`VendingSetupMenu`, `Purchase`, `art/Json`, `art/NbtWriter`) and the `getFirst()`/`getLast()` calls.
- The rule goes into `CLAUDE.md` and `docs/dev-setup.md`. It needs no separate check: the `1.20.1-forge` build fails on
  any newer syntax or API.

## 4. Forge platform code

`src/main/java/diamondvending/platform/forge/`, compiled only into the Forge jar (the other build scripts exclude it;
the Forge script excludes `platform/fabric` and `platform/neoforge`). It mirrors `platform/neoforge`:

| Piece | Forge 1.20.1 |
|---|---|
| Entrypoint | `@Mod(DiamondVending.MOD_ID)` class with a no-argument constructor; the mod bus from `FMLJavaModLoadingContext` |
| Client setup | A client class the entrypoint calls only when `FMLEnvironment.dist` is the client |
| Registration | `ForgeRegistrar` over Forge `DeferredRegister`s for blocks, items, block entities and menus |
| Menus | `IForgeMenuType.create(...)` reading the block position; opened with `NetworkHooks.openScreen(player, provider, pos)` |
| Creative tab | `BuildCreativeModeTabContentsEvent`, functional blocks tab |
| Catalogs | `AddReloadListenerEvent` |
| Sneak hint | `PlayerInteractEvent.RightClickBlock`, cancelled with `SUCCESS` like on NeoForge |
| Renderer | `EntityRenderersEvent.RegisterRenderers` |
| Tooltip | `RegisterGuiOverlaysEvent`, above `VanillaGuiOverlay.CROSSHAIR` |
| Setup screen | `MenuScreens.register` during client setup |

`Registrar.dataComponent` exists only from 1.20.5 (there are no components to register on 1.20.1).

## 5. Items and saved data on 1.20.1

1.20.1 items carry an NBT tag instead of components. Every place the mod reads or writes item data gets a 1.20.1 form;
the behaviour players see is the same.

### 5.1 Machine item color and model

- The color a machine item places is the string tag **`diamondvending:color`** (a dye name such as `"lime"`); a
  machine item without it places a red machine, as today.
- The item model switches color on **`CustomModelData`** = dye id + 1, the same numbers the 1.21.1 item model uses.
- `/give` and the QA scene scripts use NBT on 1.20.1:
  `diamondvending:vending_machine{"diamondvending:color":"lime",CustomModelData:6}`.

### 5.2 Setup kept on the item (main spec §5.4)

- Stored as the compound tag **`diamondvending:machine_setup`**, written and read with the existing
  `MachineSetup.CODEC` through NBT. As on the other versions, an item from a mod that's gone leaves only that button
  empty. A setup tag that can't be read at all is ignored with a log warning: the machine is placed empty, never half
  set up (main spec §9).
- Same rules as today: an empty setup leaves the item plain so it stacks with new machines, and infinite is kept only
  for an admin placer.

### 5.3 Matching items

- "Same item and same components" (what a button sells, stacking into slots) becomes **same item and same NBT tag** —
  Minecraft 1.20.1's own rule for stacking.
- `MachineSetup` equality and hashing follow the same rule.

### 5.4 Machine save format

- The block entity keeps the **same keys** as the main spec's saved format (map makers' `/data` commands keep working);
  items inside are in 1.20.1's item format (`id`, `Count`, `tag`).
- Saving and loading use 1.20.1's methods (no registry lookup argument). The update tag sent to clients is the same
  trimmed copy as on the other versions.
- Moving a world from 1.20.1 to 1.21.1 or later is **not supported**: machine contents would not convert. The README
  says so; it is a pack maker's concern, not a player rule, so the manual stays as it is.

### 5.5 Catalogs (main spec §5.1)

- On 1.20.1 a catalog entry's item is `{"id": ..., "count": ..., "nbt": "<SNBT>"}` — the NBT written as a string, the
  same way `/give` takes it. The shipped example catalog has a 1.20.1 copy in `resources-1.20.1/` with the enchanted
  book written that way.
- A catalog written for the other version fails closed with a log error that says how to fix it, instead of silently
  selling plain items:
  - `components` on 1.20.1 → "item components need Minecraft 1.20.5 or newer; on 1.20.1 write the item's NBT as
    "nbt"";
  - `nbt` on 1.20.5 and newer → "nbt is for Minecraft 1.20.1; on this version use "components"".
- `docs/catalogs.md` shows both forms.

### 5.6 Manual (main spec §6.2)

- Crafted by a 1.20.1 recipe whose result is a written book with the same title, author and translated pages, given as
  NBT through Forge's `nbt` recipe-result field. The pages' text is unchanged (same translation keys).
- `ManualTest` checks the 1.20.1 recipe's pages the same way it checks the others.

## 6. Block, menu and client differences

Written as small `//? if` spots in the existing classes, following the existing 1.21.1/26.1 spots:

- **Block:** 1.20.1 has `use(...)` instead of `useItemOn`, `playerWillDestroy` returns nothing, blocks have no codec,
  and the overridden block methods are `public`. Overrides are declared `public` on every version (widening is always
  allowed), which removes the need for a check there.
- **Block entity:** `saveAdditional(CompoundTag)` / `load(CompoundTag)`; `getUpdateTag()` without registries.
- **Messages and access:** the 1.21.1 forms (`displayClientMessage`, `hasPermissions(2)`) already work on 1.20.1.
- **Menu and screen:** 1.20.1 uses the same `GuiGraphics` screen methods as 1.21.1, except that a 1.20.1 screen draws
  its own dimmed background (`renderBackground(graphics)` at the start of `render`).
- **Renderer:** 1.20.1's vertex builder (`vertex(...).color(...).uv2(...).endVertex()`) in `FrontCanvas`; everything
  else in the renderer uses the 1.21.1 path.
- **Tooltip:** `HoverHud.render` takes the GUI graphics; each loader's hook adapts its own signature.
- **Codecs:** 1.20.1's DataFixerUpper lacks `validate`, `lenientOptionalFieldOf`, `ifSuccess` and `ifError`. Shared code
  uses forms every version has (`flatXmap`/`comapFlatMap` for checks, `result()`/`error()` for outcomes); only the
  lenient field reads keep a version check.

Every Minecraft API the port relies on is checked against **vanilla 1.20.1 and Forge 47.2.0** sources, not only the
NeoForge 1.21.1 ones (CLAUDE.md).

## 7. Testing

- **Unit tests** run on the new node like the others. `MetadataFloorsTest` learns the `forge` section
  (`deps.forge_loader_min` ≤ `deps.forge_loader`) and checks that the built `META-INF/mods.toml` asks for the floor.
- **GameTests:** every shared GameTest (`AllTests.ALL`) runs on `1.20.1-forge`. Forge finds them through one test class
  with `@GameTestHolder("diamondvending")` and a `@GameTestGenerator` that turns every `AllTests.ALL` entry into a test
  — no per-test adapter methods to keep in sync. The test-only mod gets a Forge `mods.toml`. Game tests run with
  `./gradlew :1.20.1-forge:runGameTestServer`, and the run must report exactly as many tests as `AllTests.ALL` holds on
  that node (so Forge's namespace filter can't quietly drop any). A test that cannot run on 1.20.1 is left out of
  `AllTests.ALL` there by a version check, with the reason written next to it.
- **Game-test structure:** the generated platform structure's `DataVersion` drops from 1.21.1's (3955) to 1.20.1's
  (3465), so one file loads on every version (newer versions upgrade it when loading); `GeneratedFilesTest` keeps it in
  step.
- The existing tests cover most of §5 once they run on 1.20.1 (machine color, setup kept on the item, stacking,
  saving). New tests, each written to fail first:
  - on 1.20.1, a machine item whose setup tag cannot be read places an empty machine and logs a warning;
  - two test catalogs sell the same enchanted book, one written with `components` and one with `nbt`: on every version
    the one written for that version loads and sells exactly that book, and the other is skipped with §5.5's error.
- The Fabric client screenshot test stays on 26.1 Fabric only.
- **CI:** `1.20.1-forge` joins the build and game-test matrix (`setup-java` adds 17); `check-jar-contents.sh` accepts the
  Forge jar and checks it holds only `platform/forge`; the uploaded artifact is the reobfuscated jar.

## 8. Release and QA

- `publishMods` in `build.forge.gradle.kts` uploads the Forge jar as loader `forge` for Minecraft `1.20.1`, under the
  same variables and secrets as the other jars (nothing is uploaded until issue #20's accounts exist).
- `tools/qa/prepare_server.py` and `scene.py` accept `1.20.1-forge`; scenes use 1.20.1's `/give` NBT syntax there.
- **Release QA** (`docs/qa-checklist.md`) runs on the 1.20.1-forge dev server and client, like the other four.
- **Floor check:** the reobfuscated release jar runs on a real **Forge 47.2.0 dedicated server** (installed with
  Forge's installer outside the repository), and the 1.20.1-forge dev client joins it and buys once.
- **Pack check:** the agent copies one of the owner's 1.20.1 Forge ATLauncher instances (the originals are never
  touched) and adds the release jar; the owner launches the copy once, since launching needs their account.

## 9. Documentation

- Main spec: §1 targets and success criteria (five jars), §8.1 targets and toolchain (JDK 17 for 1.20.1), §10 "all five
  targets", §11 drops "Forge 1.20.1"; `docs/backlog.md` marks #2 done.
- `docs/dev-setup.md`: the node, Java 17, the `forge` constant and the `<1.20.5` checks, running the Forge game tests.
- `docs/catalogs.md`: the 1.20.1 `nbt` form (§5.5).
- `README.md`: supported versions, and the note that 1.20.1 worlds do not move to 1.21.1 with machine contents.
- `CHANGELOG.md`: 1.1.0 — "Forge 1.20.1 support".
- `CLAUDE.md`: shared code is Java 17; loader-only code includes `platform/forge/`.
- No new player rules, so the manual text does not change (CLAUDE.md's manual rule is satisfied).

## 10. Out of scope

- **Fabric 1.20.1** — one of the owner's packs; a follow-up node reuses this port's `<1.20.5` checks.
- **The NeoForge 1.20.1 fork** — not built against or tested, so not claimed.
- **Moving 1.20.1 worlds to newer versions** with machine contents (§5.4).
- **Adding Forge 1.20.1 to mc-mod-template** — after this ships, from what it teaches.

## 11. Risks

| Risk | Plan |
|---|---|
| ModDevGradle Legacy Forge together with Stonecutter 0.9.8 on Gradle 9.7 is untried here | The plan's first task is a build spike: node configures, Minecraft artifacts are created, an empty jar reobfuscates. If it cannot work, stop and bring the owner a fallback (e.g. Architectury Loom) before any porting |
| An API guessed from 1.21.1 memory is wrong on 1.20.1 | Each plan task is written against the decompiled 1.20.1 and Forge 47.2.0 sources from the spike, and the GameTests run on the node |
| Forge's `nbt` recipe result may not reach the shapeless serializer in 47.2.0 | A GameTest crafts the manual on 1.20.1 and checks its pages; fallback is a small Forge recipe serializer registered only in the Forge jar |
| Shared code drifts back to Java 21 later | The 1.20.1 node's CI build fails on it |
